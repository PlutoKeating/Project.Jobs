# 飞书渠道重构：Jobs Agent（2026-11-17）

> 状态：产品负责人于 2026-11-17 逐题回答 22 道题后拍板，并要求「先落盘所有工作计划和拍板决策，然后立即开始实现，全部实现」。本文是这次重构的唯一决策记录：§1–§4 是调研与决策原文，§5 是实现计划，§6 是落实情况（实现过程中回写）。与 [`DECISIONS_2026-11-15.md`](DECISIONS_2026-11-15.md) 第 28、31 题冲突时以本文为准；实现与本文不一致时以代码为准并回写 §6。

## 1. 出发点

使用者是大量用 Jobs 测新软件的 AI Native 全栈开发者。他常常不在电脑前：中午出去吃饭、下班回家的路上。飞书在手机上做得好，是这时唯一顺手的入口。IM 最直觉的交互是**说话**，所以飞书里不该是一套要背的命令，而是一个原生接好 Jobs 全部能力的 agent。

重构前（`apps/api/src/feishu.ts`，216 行）：正则解析 8 个固定命令；回复是纯文本；主动推送靠每 20 秒查一次库，每个人用完都推一条；扫码之后的收发与推送没有在真实账号上跑过。

## 2. 调研结论（含一手的 SDK 类型定义）

| 来源 | 借鉴什么 |
|---|---|
| 飞书官方 `@larksuiteoapi/node-sdk` 1.76 的 `LarkChannel`（`createLarkChannel`） | **直接用它做渠道层，不自己造**：长连接、消息归一化（`NormalizedMessage`：文字、资源、@、话题 `threadId`）、去重、过期消息丢弃、按聊天排队、私聊 / 群 @ 策略、`send`（markdown / 卡片 / 图片 / 文件）、`stream`（CardKit 流式卡片，自带节流，单个元素超长时自动接一张新卡）、`updateCard`、卡片回调 `cardAction`、`downloadResource`、`botAdded` |
| 同一 SDK 的 `registerApp` | 扫码一键创建应用时用 `addons` 追加权限、事件、回调（`card.action.trigger`）；**传 `appId` 可以对已有应用再扫一次码补权限**（确认页展示差异），不必新建应用 |
| OpenClaw 飞书插件（飞书开放平台团队维护）、Hermes Agent | 卡片三态（思考中 / 输出中 / 完成）；私聊每句都回、群里 @ 才回；配对码 / 白名单；敏感操作用卡片按钮确认（Hermes：允许一次 / 本次会话 / 始终 / 拒绝）；「设为推送目标」的会话；卡片回调必须在开发者后台订阅，否则点按钮报 200340 |
| 社区的流式输出踩坑记录 | 用编辑消息接口更新同一条消息，二三十次后会静默失败；要用 CardKit 卡片实体，节流更新 |
| Pi（`@earendil-works/pi-agent-core`，原 `@mariozechner/pi-agent-core`） | 精简的 agent 循环：工具调用、`beforeToolCall` / `afterToolCall`、`steer`（干活中途插话）、`followUp`、`abort`、事件流（驱动卡片）。`streamFn` 可替换，所以模型调用仍走我们自己的路由（花费记录、失败接替、网页里配置的模型都照旧）。核心不内置 MCP，工具直接用 `launch/tools.ts` 的同一份定义 |
| cc-connect、botmux 等 | 把整个 coding agent CLI 接到 IM；形态不同，只参考会话与权限设计 |
| Telegram Bot 设计指南、聊天审批的实践 | 带参数的命令对普通用户不直觉；审批按钮单次有效、有明确状态、会过期；按下按钮必须立刻应答 |

## 3. 拍板决策（22 题）

### 3.1 定位与形态

| # | 题目 | 决定 |
|---|---|---|
| 1 | 移动场景优先级（多选） | **全部四类**：随时掌握动态；远程操作发布；深挖证据；处理介入与分享 |
| 2 | 交互范式 | **自然语言为主 + 卡片按钮**；另有机器人菜单与少量控制命令（`/new`、`/stop`）；原有的正则命令全部去掉 |
| 3 | Agent 归属 | **不绑定渠道的核心**：飞书 + 网页聊天面板 + `jobsworld chat` 都接它，会话在各端互通 |
| 4 | Harness | **pi-agent-core + 自家 `packages/llm`**（先给 llm 补上工具调用与流式输出） |

### 3.2 权限、群聊与会话

| # | 题目 | 决定 |
|---|---|---|
| 5 | 谁能用 | **「1+3」**：扫码的人是管理员；同一飞书组织的其他人默认是访客（只读）；发口令配对，管理员口令升为管理员、访客口令绑定为访客；网页里能看、能撤销已绑定的人；换口令后绑定全部失效 |
| 6 | 群聊 | **「1+3」**：@ 才回；一个群共用一份上下文；在话题里说话，每个话题是一段独立的对话；每句话按说话人自己的角色限权；可以把某个群设为推送去处 |
| 7 | 写操作确认 | **只有破坏性的确认**：清零、下线弹「确认 / 取消」卡片（按钮只能点一次，30 分钟过期）；花钱的不拦（与「不设花费上限」一致） |
| 8 | 对话记忆 | **每个聊天一条长期会话，自动压缩**；`/new` 重新开始；记录存在 Postgres，跨重启保留；推送也计入上下文（可以直接回一句「这个人为什么放弃」） |

## 4. 架构

```text
飞书（LarkChannel）  网页聊天面板（SSE）  jobsworld chat（SSE）
        │                    │                    │
        └──────── 渠道适配：把消息 → AgentInput，把 AgentEvent → 卡片 / 流 ────────┘
                                   │
                    packages/agent（@pux/agent）
   AgentHub：每个会话键一个 pi Agent；忙时 steer；会话存 Postgres、自动压缩
   身份与限权：说话人 → 管理员 / 访客；工具按角色过滤；破坏性工具走确认
   工具 = @pux/engine 的 JOBS_TOOLS（与 MCP、CLI 同一份）+ 渠道工具（导出云文档、跟居民聊、推送偏好）
   streamFn → @pux/llm gateway().converse()（工具调用 + 流式；失败接替只在第一个字出来之前）
                                   │
             工具经 REST（app.inject，带说话人的身份）→ /api/v1/*
```

- **会话键**：`feishu:<chat_id>`（私聊、群）、`feishu:<chat_id>:<thread_id>`（话题）、`web:<登录者>`、`cli:<登录者>`。网页与命令行在同一个管理员身份下共用一条会话；飞书管理员可以在网页里看到自己飞书私聊的那条。
- **推送**：引擎在关键时刻往 NATS `jw.notice` 发一条事件（使用结束、问题第一次出现、结论写好、需要人介入）；API 里的推送器订阅它，按偏好决定实时发、合并发或进早报晚报，并刷新各产品的看板卡。
- **飞书权限（扫码时追加）**：机器人收发与私聊 / 群 @ 消息、`im:resource`（下载图片和文件）、`im:message.urgent`（应用内加急）、`cardkit:card:write`（流式卡片）、`im:chat:readonly`（群信息、话题模式）、`contact:user.base:readonly`（说话人名字）；事件 `im.message.receive_v1`、`im.chat.member.bot.added_v1`、`application.bot.menu_v6`；回调 `card.action.trigger`；用户身份 `docx:document`、`drive:drive`（导出云文档，第一次用时授权）。
